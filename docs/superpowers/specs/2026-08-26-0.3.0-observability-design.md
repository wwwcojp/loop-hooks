## 1. 何を作るか、なぜ作るか

0.2.1 までで「エージェントに回避されない変更駆動ゲート」は成立した。0.3.0 は、そのゲートが
**期待どおりに動いているかを利用者が確認できる**ようにする。動機は運用で観測された3つの事実:

1. **ゲートは無言で消えることがある。** フック定義はセッション開始時のスナップショットなので、
   プラグインの入口ファイルが動く・プラグインが読めなくなると、稼働中セッションではゲートが
   走らなくなるが、何も表示されない(safe-dev-hooks `dogfooding.md` に記録。0.2.0 で
   `hooks/stop/gate.py` → `hooks/gate.py` の移動時に実際に発生)。
2. **`watch` の既定が TypeScript 固定で、Python リポジトリが `watch` を書き忘れると無言で
   ゲートが掛からない。** 利用中3プロジェクトのうち2つは Python。既定は安全側であるべき。
3. **プラグイン自身は「走らなかった理由」を一切残さない。** 0.2.1 の分析は runner 側の
   evidence に頼った。skipped / disabled / ran の判定はどこにも記録されず、事象1のような
   問題がデバッグ不能。

三者に共通する原則: **静かな失敗を無くす。** ゲートが有効ならそう言う、無効ならなぜかを言う、
走らなかったなら理由を残す。

| `hooks/session_start.py` | SessionStart で設定を検証し、ゲートの有効/無効を告知する。**検証コマンドは実行しない** | 新規 |
| `hooks/lib/config.py` | 設定の読込・検証 | 変更(既定値、`_source` の付与) |

| `hooks/lib/status.py` | 状態の収集(`collect`)と整形(`render`)。`gate.py --status` と SKILL.md が共用 | 新規 |

設計上の制約:

- **`gate.py` は動かさない。** 入口ファイルの移動は稼働中セッションのフック登録を壊す(§1 事象1)。
- 入口は「Claude Code から呼ばれる単位」で分け、ロジックは `lib` に置いてテストする(既存の構造を維持)。
- `lib` の各モジュールは例外を外に出さない。ログ書込の失敗がゲートの判定に影響してはならない。

## 3. SessionStart フック(確認済み)

### 3.1 登録

`hooks.json` に `SessionStart` エントリを追加。matcher なし(全 `source`: startup / resume /
clear / compact / fork)、`timeout: 30`、`statusMessage: "loop-hooks: checking gate"`。

`compact` を含めるのは、要約で `additionalContext` が失われるため再注入が要るから。

### 3.2 処理

1. `fingerprint.repo_root(cwd)` でルートを解決し、`config.load(root or cwd)` を呼ぶ。
2. 状態ごとに出力する。**検証コマンドは実行しない**(起動を遅らせない)。

| 状態 | エージェント向け `hookSpecificOutput.additionalContext` | 人間向け `systemMessage` |
|---|---|---|
| 設定なし(`load` が None) | 出さない | 出さない(オプトインの原則) |
| 有効 | 告知文(§3.3) | `[loop-hooks] gate active: <command>` |
| 有効かつ `_notice` あり | 告知文 | `gate active` の行 + 通知の行 |
| 設定エラー(`_error`) | 出さない | `[loop-hooks] gate disabled: <理由>` |
| git リポジトリでない | 出さない | `[loop-hooks] gate disabled: not a git repository (<cwd>)` |

3. 判定ログに1行記録する(§5.1。`event=SessionStart`、`source`、`decision` は
   `announced` / `disabled` / `none`)。

### 3.3 告知文

公式の指針(「命令形ではなく事実文で書く。システム命令風の文はプロンプトインジェクション
防御に引っかかる」)に従う。

```
loop-hooks is active in this repository. When a turn ends and a watched file has
changed since the gate last passed, `<command>` runs from the repository root; if
it fails, its output is returned and the turn stays open until it passes.
Events: <on を , 区切り>. Watched: <watch>. Ignored: <ignore>.
Configuration is read from the committed .loop-hooks.json.
```

最後の一文は、設定を書き換えて回避しようとする動機を先に断つためのもの(0.2.1 で HEAD 版
優先にした事実の告知)。

### 3.4 通知の重複排除との関係

SessionStart では `_notice` を state の `noticed` に**書かない**。SessionStart の通知は
セッションごとに毎回出てよく、Stop 側の「ゲート実行時に一度だけ」の規則を消費させない。

### 3.5 エラー処理

`handle()` の外側で全例外を握り、何も出さずに exit 0。起動をブロックする事故を起こさない。

## 4. 既定値の変更(破壊的変更)

### 4.1 新しい既定

```json
"watch":  ["*"],
"ignore": ["node_modules/*", "*/node_modules/*", ".venv/*", "*/.venv/*",
           "dist/*", "build/*", "target/*", ".claude/*", ".loop/*", "*.md"]
```

- `watch` 既定 `["*"]`: fnmatch の `*` は `/` をまたぐので「全ファイル」。
- `ignore` に `*/node_modules/*` の形を併記するのは、`node_modules/*` がルート直下しか
  一致しないため(モノレポの `packages/a/node_modules/`)。`.venv` も同様。`dist` / `build` /
  `target` はルート直下のみ(ネストは利用者が足す)。
- `*.md` を含める(チャットで合意): ドキュメントのみの変更でゲートを走らせない。利用中
  3プロジェクトのうち2つが明示的に `*.md` を ignore しており、現行既定とも一致する。
  docs をテストするリポジトリは `ignore` を上書きする。
- lockfile(`package-lock.json`、`uv.lock` 等)は既定で **watch 対象のまま**。依存の変更は
  検証に値し、README の主張(「lockfile の更新も捕捉する」)とも整合する。

### 4.2 影響

- `watch` を省略しているリポジトリは、TS 系ファイルだけでなく全ファイルの変更でゲートが
  走るようになる。ゲートが走る頻度は上がるが、走らないより安全。
- 利用中3プロジェクトは全て `watch` / `ignore` を明示しているため影響なし。
- README の既定値の表と、設定例の `watch` の説明を更新する。

## 5. 判定ログと status

### 5.1 判定ログ `hooks/lib/log.py`

**置き場**: state と同じディレクトリ、`<state_dir>/<key>.log.jsonl`(`key` は state と同じ
リポジトリパスの sha256 先頭16桁)。リポジトリには書かない(0.2.0 の契約を維持)。

**1行の形**:

```json
{"ts":"2026-08-26T09:12:03Z","event":"Stop","decision":"ran","result":"pass","ms":2140,"fp":"9f2c1a3b7e0d"}
{"ts":"2026-08-26T09:05:41Z","event":"Stop","decision":"skipped","fp":"9f2c1a3b7e0d"}
{"ts":"2026-08-26T08:58:10Z","event":"SessionStart","source":"startup","decision":"announced"}
{"ts":"2026-08-25T18:40:22Z","event":"Stop","decision":"disabled","note":".loop-hooks.json: gate.command must not be empty"}
```

| フィールド | 値 |
|---|---|
| `ts` | UTC ISO 8601(秒精度) |
| `event` | `Stop` / `SubagentStop` / `TeammateIdle` / `SessionStart` |
| `source` | SessionStart のみ |
| `decision` | `none`(設定なし)/ `disabled`(エラー・非git)/ `off`(`gate.on` 対象外)/ `skipped`(指紋一致)/ `ran` / `announced` |
| `result` | `ran` のとき `pass` / `fail` / `warn`(二重ブロック回避・再入で通した) |
| `ms` | `ran` のときコマンド所要時間 |
| `fp` | フィンガープリント先頭12桁(`skipped` / `ran` のとき) |
| `note` | `disabled` の理由、`_notice` の要約(80字まで) |

**上限**: 1200 行を超えたら直近 1000 行に切り詰める(償却的に O(1))。

**契約**: `log.append(root, record)` は例外を投げない。ディレクトリ作成失敗・書込失敗は黙って
捨てる。`log.tail(root, n)` は最新 n 件を新しい順に返し、壊れた行は飛ばす。

**記録の責務**: `gate.handle()` と `session_start.handle()` が、判定が確定した箇所で1回だけ
`log.append` を呼ぶ。`--status` は記録しない。

### 5.2 `config.load` の拡張

戻り値に `_source` を足す: `"HEAD"` / `"working-tree"`。status 表示に使う。既存の
`_error` / `_notice` と同じく、`gate` キーの外側に置く。

### 5.3 状態の収集 `hooks/lib/status.py`

`collect(cwd) -> dict` は、ゲートと同じ経路(`repo_root` → `config.load` → `fingerprint.compute`
→ `state`)を辿って次を集める。**コマンドは実行しない。**

```
root, config_source, config_error, notice,
command, on, watch, ignore, timeout_sec,
fingerprint, verified, will_run(bool), blocked(bool), noticed,
recent: log.tail(root, 5)
```

`render(info) -> str` は人間向けの固定幅テキストを返す:

```
loop-hooks status
  repo      /home/alice/my-project
  config    HEAD (.loop-hooks.json)
  command   uv run python scripts/verify.py quick
  on        stop, subagent_stop, teammate_idle
  watch     *.py, pyproject.toml
  ignore    .loop/*, *.md
  timeout   300s
  state     changed since last pass -> gate will run at next stop
  blocked   no
  recent    2026-08-26 09:12  Stop          ran      pass   2.1s
            2026-08-26 09:05  Stop          skipped
            2026-08-26 08:58  SessionStart  announced
```

設定なし・エラー・非 git の場合もそれぞれ1行で理由を出す(空出力にしない)。

### 5.4 `gate.py --status [path]`

`sys.argv[1] == "--status"` なら stdin を読まず、`path`(省略時はカレントディレクトリ)で
`status.collect` → `render` を stdout に出して exit 0。エラー時も exit 0(表示ツールであって
判定ツールではない)。フック経由の通常実行(引数なし)には影響しない。

### 5.5 スキル `skills/status/SKILL.md`

```markdown
---
name: status
description: Show whether the loop-hooks verification gate is active in this repository, what it runs, and why it did or did not run recently
allowed-tools: Bash(uv run "${CLAUDE_PLUGIN_ROOT}/hooks/gate.py" *)
---

!`uv run "${CLAUDE_PLUGIN_ROOT}/hooks/gate.py" --status "${CLAUDE_PROJECT_DIR}"`

The block above is the current state of the loop-hooks gate for this repository.
Report it to the user as-is. This skill is read-only: it does not change
`.loop-hooks.json` or the gate.
```

- `` !`…` `` 構文により、モデルがツールを呼ぶ前に出力が注入される(決定論的)。
- `${CLAUDE_PLUGIN_ROOT}` / `${CLAUDE_PROJECT_DIR}` はプラグインスキルの本文で置換される
  (公式リファレンスで確認済み)。`cwd` は `cd` で動くため、`${CLAUDE_PROJECT_DIR}` を明示。
- 呼称は `/loop-hooks:status`(プラグイン名 + frontmatter の `name`)。
- 利用者・モデルの双方から呼べる(既定)。読取専用なのでモデルが呼んでも害はなく、
  「なぜゲートが走らなかったか」を聞かれたときに使える。
