loop-hooks における loop engineering の実践

エージェントのターン終了をリポジトリの検証コマンドで判定する Stop hook プラグイン loop-hooks を、そのプラグイン自身の開発に適用し、5 段階で検証内容を拡充した記録。構成、運用データ、各検証器の役割と本リポジトリでの貢献を整理する。

対象 wwwcojp/loop-hooks 期間 3 日 / 0.3.1 → 0.7.0 テスト 169 → 337 mutants 936、kill 率 95.5%

01背景: ループの停止条件

Osmani の定義では、loop engineering はエージェントへ直接 prompt を書く段階から、エージェントを駆動する系(trigger、schedule、worktree、subagent、memory)を設計する段階への移行を指す。Orosz の調査が示すとおり、その大部分は orchestration の領域だが、系の一点は設計の質が結果の質を直接決める。何がループの終了を判定するかである。

作業を行ったモデル自身、または review を依頼した第二のモデルに終了判定を委ねると、判定は確率的なままであり、未完了の作業に対して "done" を返しうる。SonarSource はこの点を「検証のない loop engineering は単なる自動化」と整理し、Osmani とともに対策としてdeterministic verification tier(意見を返す verifier ではなく、作業を fail させられる check)を推奨している。

loop-hooks はこの tier の最小実装である。エージェントがターンを終了しようとした時点で、リポジトリが持つ検証コマンドを実行し、失敗時はその出力を additionalContext(Claude Code hooks reference)として返してターンを継続させる。プラグインは検証ロジックを持たず、検査内容は .loop-hooks.json でリポジトリ側が定義する。

設計判断は 3 点。(1) 方針は CLAUDE.md、省略不可の検査は hook に置く — 前者は context summarization や推論で欠落しうるが、後者は必ず実行される。(2) プラグインは検証ロジックを持たない — 言語や stack に依存せず、ゲートの強化はリポジトリ側の変更になる。(3) 検証は commit 単位ではなくターン単位 — pre-commit hook は commit がなければ発火せず、CI は数分後にループ外で報告する。Stop hook は失敗を生んだ context をエージェントが保持しているうちに返す。

02構成: ターン単位の stop gate

Stop / SubagentStop / TeammateIdle の各 hook event で同じ判定を行う。ターンごとの実行コストは fingerprint による変更検知で抑制する。

HOOK EVENTStop / SubagentStop / TeammateIdle
→
FINGERPRINTgit status と content hash から watch 対象の状態を算出し、前回 pass 時の記録と比較
→
VERIFYuv run python scripts/verify.py quick をリポジトリルートで実行(設定は HEAD 版を優先、timeout 300 s、process group ごと kill)
PASS — 実行後の fingerprint を verified として記録しターンを終了する。次のターンで fingerprint が一致すれば実行しない(skipped)。
FAIL — 出力の先頭 2,500 字と末尾 5,500 字を additionalContext(TeammateIdle は exit 2 + stderr)で返し、ターンを継続させる。同一 fingerprint は 2 度 block しない(warn で通過、無限ループ防止)。

fingerprint が算出できない場合(git が観測不能)は実行側に倒す。skipped に倒すとゲートが無言で無効化されるため。

設定の HEAD 優先

エージェントは working tree の .loop-hooks.json を書き換えられる(command を true にする、ファイルを破壊する)。このためゲートは commit 済みの設定を読み、working tree 版との差異は通知のみ行う。この不変条件は第 1 段階でテスト化し、第 5 段階の contract test で再確認した。

03dogfooding: 運用データ

382 回は fingerprint 一致により skipped(未実行)。実行の 77% は SubagentStop で発生した。read-only の reviewer subagent の終了時に、並行する implementer subagent の未 commit 変更(未使用 import、行長超過、RED 状態のテスト)でゲートが fail した例を含む。ゲートは変更の作成者を区別しないため、同一ファイルに触る implementer を並行させない運用に変更した。

自己参照リポジトリの運用規約

  • セッションが使用するプラグインは GitHub 版(marketplace source: github)。working tree の破損した gate.py がゲート判定を行ってはならない。working tree のコードは verify runner 経由の pytest でのみ実行される。
  • entry file(hooks/gate.py・hooks/session_start.py・hooks/hooks.json)を移動しない。hook 定義はセッション開始時の snapshot であり、移動するとゲートが無言で消える。移動する場合は release note に再起動要件を明記する。
  • ゲートで止められたらコードを修正する。.loop-hooks.json の変更や disableAllHooks で通過しない。設定は HEAD 版が優先されるため working tree の変更は効かない。
  • ゲートの検査内容は CI と同一。quick は CI の test job と同じ 6 check であり、乖離は test_quick_stage_mirrors_ci が検出する。

04段階的導入と各段階で検出した欠陥

各段階は独立に価値を持ち、段階ごとに運用してから次段階を判断した。「検出した欠陥」はその段階の検査を導入した結果として発見されたものである。

mutation testing + ratchet

mutmut で hooks/lib の 6 ファイルを対象に mutation testing。ファイル単位の killed 件数を baseline と比較し、減少で fail(許容 1 件、total 変化時は re-baseline)。baseline は runner のみが更新する。

40.6.0

06開発プロセス側のループ

コードのループ(turn → gate)の外側に、開発プロセスのループがある。各段階は brainstorming → 子 spec → implementation plan → Subagent-Driven Development(SDD)で進めた。task ごとに新規の implementer subagent を起動し、read-only の reviewer subagent が spec 適合と品質を判定する。指摘は同一 implementer に返して fix round(最大 5 回)を回し、最後に branch 全体の review を行う。controller の裁定はすべて ledger に記録する。

ゲートは SDD の subagent にも作用した。reviewer の終了時に SubagentStop で quick が走り、並行中の implementer の未 commit 変更で fail する。これを受けて、同一ファイルに触る implementer を並行させない、reviewer には read-only を明記する、implementer には foreground 実行と subagent 禁止を明記する、という運用に固定した。

ledger に記録した裁定の例

  • 第 4 段階: 「6 property すべてが mutant を 1 件以上 kill する」を当初「文字どおりには未達」と裁定。最終 review で property 単独の測定を行い達成を確認し、裁定を訂正して記録。
  • 第 5 段階: 判定一致テストが lib の欠陥を検出。「欠陥が見つかった場合のみ lib を修正する」制約に従い修正、CHANGELOG の Fixed に記載、mutation baseline を re-baseline。
  • 第 3 段階: 無限ループ化する mutant に pragma: no mutate を付けず、loop を iterator に書き換えて mutant 自体を生成不能にした。

07まとめ

  1. 停止条件は系の構成要素として設計する。モデルの自己申告ではなく、リポジトリが持つ検査に判定させる。検査内容はリポジトリが所有し、プラグインはターンを閉じるか否かのみを制御する。
  2. ゲートは自リポジトリにも適用する。3 日間で 62 回の fail をターン内で返却した。ゲートを作る側が最もゲートを必要としていた。
  3. 検証内容は段階的に拡充する。各段階の検査は導入直後に固有の欠陥を検出した。一括導入では検出元の対応が取れない。
  4. 実行時間で層を分ける。ゲートは 30 秒以内、それ以外は all。遅いゲートは無効化される。
  5. 変更検知で未実行を作る。256 回の実行に対し 382 回が skipped。検知がなければ毎ターン 12 秒を消費する。
  6. 不変条件はテストとして記述する。「HEAD 優先」「書込先はリポジトリ外」「entry は lib のみ import」は、記憶や CLAUDE.md の文章ではなく fail するテストで維持する。
  7. 裁定は ledger に残す。自律実行中に決めた事項と、誤りだった場合の代償を記録し、人が後から見直せるようにする。
